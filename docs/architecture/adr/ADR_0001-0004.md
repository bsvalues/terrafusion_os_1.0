## ADR-0001: Property Workbench is Tier-0 OS Surface

### Status
**ACCEPTED** — 2026-01-28

### Context

TerraFusion has multiple functional suites (TerraForge, TerraAtlas, TerraDais, TerraDossier) that all need to interact with parcel data. Without clear architectural guidance, each suite would build its own "parcel screen," leading to:

- **Fragmentation:** Multiple parcel UIs with inconsistent behavior
- **Data Duplication:** Each suite maintaining its own parcel state
- **User Confusion:** "Where do I go to work on this parcel?"
- **Maintenance Burden:** Changes to parcel data model require updates in multiple places
- **Future Office Collision:** When Clerk/Treasurer/Auditor suites arrive, they would add more parcel screens

### Decision

**Property Workbench is a Tier-0 OS Surface**, not owned by any suite.

| Aspect | Decision |
|--------|----------|
| Tier | 0 (OS Core) |
| Ownership | TerraFusion OS, not any suite |
| Structure | Single shell with suite-contributed tabs |
| URL Pattern | `/property/:parcelId` (canonical) |
| Tab Order | Summary → Forge → Atlas → Dais → Dossier → Pilot |
| Integration | Suites register tabs via plugin API |

### Consequences

**Benefits:**
- Single source of truth for parcel interaction
- Consistent user experience across roles
- Clean architecture: suites own their lane, OS owns the shell
- Deterministic future office integration

**Trade-offs:**
- Suites must migrate existing parcel screens to tab pattern
- Tab plugin API adds abstraction layer
- Property Workbench team becomes critical path for parcel features

### Compliance

This decision aligns with:
- County data sovereignty (single parcel truth)
- FISMA audit requirements (unified trace)
- Accessibility standards (consistent navigation)

## ADR-0002: Suite Ownership + Write-Lane Matrix

### Status
**ACCEPTED** — 2026-01-28

### Context

TerraFusion suites share parcel context but manage different data domains. Without clear ownership rules:

- **Data Conflicts:** Two suites could update the same field
- **Audit Gaps:** Unclear who is responsible for data integrity
- **Permission Confusion:** Role-based access becomes ambiguous
- **Integration Complexity:** Cross-suite features have no contract

### Decision

**Each data domain has exactly ONE write owner.** Other suites can read but must use service APIs to trigger writes in other domains.

#### Suite Mission Statements

| Suite | Mission | Write Domain |
|-------|---------|--------------|
| TerraForge | Build value | Valuation artifacts, models, comps, CAMA |
| TerraAtlas | See the county | GIS artifacts, layers, boundaries |
| TerraDais | Operate value | Workflows, notices, certifications |
| TerraDossier | Prove the decision | Documents, narratives, packets |
| OS Core | Platform truth | Identity, trace, system state |

#### Write-Lane Matrix

| Data Domain | Write Owner | Others Can |
|-------------|-------------|------------|
| Parcel Identity | OS Core | Read |
| Ownership Records | OS Core | Read |
| Valuation Artifacts | TerraForge | Read |
| CAMA Characteristics | TerraForge | Read |
| GIS Artifacts | TerraAtlas | Read |
| Workflow States | TerraDais | Read |
| Documents | TerraDossier | Read |
| Trace Events | TerraTrace | Emit only |

#### Cross-Suite Protocol

```typescript
// Example: TerraDais needs to create a document
// CORRECT: Use Dossier service
await DossierService.createDocument({ ... });

// WRONG: Direct database access
await db.dossier_documents.insert({ ... }); // ❌ FORBIDDEN
```

### Consequences

**Benefits:**
- Clear data ownership prevents conflicts
- Audit trail can attribute changes to responsible suite
- Permission model is unambiguous
- Service boundaries enforce clean architecture

**Trade-offs:**
- Cross-suite features require service calls
- Must maintain service APIs as contracts
- Latency for cross-suite writes (minimal in practice)

### Compliance

This decision aligns with:
- FISMA data integrity requirements
- County data sovereignty model
- Single-writer principle for consistency

## ADR-0003: TerraTrace is Unified Append-Only Audit Spine

### Status
**ACCEPTED** — 2026-01-28

### Context

Government operations require comprehensive audit trails for accountability and compliance. Previous approaches had:

- **Suite-Specific Logs:** Each suite maintained its own logging
- **Inconsistent Format:** Different event schemas across loggers
- **Query Complexity:** Reconstructing activity required joining multiple sources
- **Compliance Risk:** Logs could be modified or deleted

### Decision

**TerraTrace is the unified, append-only audit spine for all suite actions.** Every write action across all suites emits a TraceEvent to a single, immutable log.

#### Core Principles

| Principle | Implementation |
|-----------|----------------|
| Append-Only | No UPDATE or DELETE on trace_events table |
| Immutable | Hash chaining for tamper detection |
| Unified Schema | Single TraceEvent model for all suites |
| Separated Events | `action_started` + `action_completed/failed` pattern |
| Redaction Support | PII can be redacted; event shell remains |

#### TraceEvent Model

```typescript
interface TraceEvent {
  id: string;                  // UUID v7 (time-sortable)
  timestamp: DateTime;
  countyId: string;            // Tenant isolation
  parcelId: string | null;
  dossierId: string | null;
  
  actor: {
    userId: string;
    userName: string;
    role: UserRole;
    pilotSessionId?: string;
  };
  
  event: {
    suite: SuiteName | "os";
    module: string;
    action: string;
    category: "valuation" | "workflow" | "compliance" | "system";
  };
  
  data: {
    inputs: Record<string, any>;
    outputs: Record<string, any>;
    evidenceLinks: string[];
  };
  
  compliance: {
    classification: "PUBLIC" | "INTERNAL" | "CONFIDENTIAL" | "RESTRICTED";
    retention: RetentionPolicy;
    piiPresent: boolean;
  };
  
  chainHash: string;           // SHA-256 of previous event + this event
}
```

#### Immutability Rules

1. **No Updates:** Events cannot be modified after creation
2. **No Deletes:** Events cannot be removed (except legal holds)
3. **Chain Integrity:** Each event includes hash of previous event
4. **Redaction:** PII marked with `[REDACTED]`, event structure preserved

#### Retention Policies

| Policy | Duration | Use Case |
|--------|----------|----------|
| session | Session end | Navigation events |
| 30_days | 30 days | Temporary operations |
| 1_year | 1 year | Standard activity |
| 7_years | 7 years | Audit-relevant actions |
| permanent | Never | Certification, legal |

#### Redaction Protocol

```typescript
// Redaction preserves event but obscures PII
interface RedactedEvent extends TraceEvent {
  redacted: true;
  redactedAt: DateTime;
  redactedBy: string;
  redactedReason: string;
  originalDataHash: string;    // Prove original existed
  
  data: {
    inputs: { pii_field: "[REDACTED]", ... };
    outputs: { pii_field: "[REDACTED]", ... };
    evidenceLinks: string[];
  };
}
```

### Consequences

**Benefits:**
- Complete audit reconstruction from single source
- Tamper-evident chain
- Consistent format for all events
- Powers Activity Feed in Property Workbench
- Meets FISMA-High audit requirements

**Trade-offs:**
- Storage grows indefinitely (requires archival strategy)
- All suites must emit trace events (enforcement required)
- Query performance requires proper indexing
- Redaction adds complexity

### Compliance

This decision aligns with:
- FISMA-High AU-2 (Audit Events)
- FISMA-High AU-3 (Audit Record Content)
- NIST 800-53 audit controls
- County record retention policies

## ADR-0004: TerraPilot is OS Feature with Pilot/Muse Modes + Tool Safety

### Status
**ACCEPTED** — 2026-01-28

### Context

TerraFusion had two AI assistant systems with overlapping responsibilities:

- **TerraAssistant:** UI/chat interface for users
- **TerraAgent:** Backend tool execution engine

Users were confused about which system to use, and the systems had inconsistent safety controls for tool execution.

### Decision

**Consolidate TerraAssistant and TerraAgent into TerraPilot**, a single OS-level personal copilot with two operational modes and comprehensive safety controls.

#### Architectural Consolidation

| Old System | New Location | Status |
|------------|--------------|--------|
| TerraAssistant | TerraPilot UI components | Merged |
| TerraAgent | TerraPilot runtime engine | Merged |

#### Two Operational Modes

| Mode | Purpose | Focus |
|------|---------|-------|
| Pilot Mode | Operator | Do, route, act, execute |
| Muse Mode | Creator | Draft, explain, synthesize |

**Key Insight:** Muse is a mode within TerraPilot, not a separate product. Users have ONE copilot that can operate in two modes.

#### Tool Risk Levels

| Risk Level | Description | Controls |
|------------|-------------|----------|
| read | Read-only, no side effects | None |
| write-low | Creates drafts, internal records | Optional confirmation |
| write-medium | Modifies data, reversible | Required confirmation |
| write-high | Official actions, sends notifications | Confirmation + reason code |
| irreversible | Certification, publishing | Confirmation + reason + supervisor |

#### Human-in-the-Loop Gates

```
Tool Invocation → Permission Check → Risk Assessment →
  [read/write-low] → Execute
  [write-medium] → Confirmation Dialog → Execute
  [write-high] → Confirmation + Reason Code → Execute
  [irreversible] → Confirmation + Reason + Supervisor Approval → Execute
```

#### All Actions Logged to Trace

Every TerraPilot tool invocation emits:
1. `tool_invoked:{toolId}` — Before execution
2. `tool_completed:{toolId}` OR `tool_failed:{toolId}` — After execution

### Consequences

**Benefits:**
- Single, coherent copilot experience
- Clear mode distinction (doing vs. creating)
- Government-grade safety controls
- Complete audit trail via Trace
- Playbooks enable automation with guardrails

**Trade-offs:**
- Safety gates add friction for power users
- Two modes require clear UI indication
- Consolidation requires migration of legacy systems

### Compliance

This decision aligns with:
- Human oversight requirements for AI systems
- FISMA principle of least privilege
- Audit trail requirements for all actions
- Government accountability standards
