## ADR-0001: Property Workbench is Tier-0 OS Surface

**Status:** ACCEPTED  
**Deciders:** TerraFusion Architecture Team  
**Date:** 2026-01-28  

### Context

TerraFusion OS has multiple suites (Forge, Atlas, Dais, Dossier, GPT) that all need to interact with parcel data. Without a canonical parcel interaction point, each suite would build its own "parcel screen," creating:

- **Data fragmentation** - multiple sources of truth for parcel state
- **User confusion** - different UIs for the same parcel depending on entry point
- **Implementation drift** - suites diverging on parcel presentation
- **Maintenance burden** - N parcel screens instead of 1

### Decision

**Property Workbench is a Tier 0 OS Surface** - a core operating system component that serves as the canonical parcel interaction point for ALL suites.

**Key Principles:**

1. **OS-Owned, Not Suite-Owned**
   - Property Workbench lives at `os-platform/core/property-workbench/`
   - No suite owns the Workbench - it is neutral infrastructure
   - Suites integrate via extension API, not direct modification

2. **Single URL Pattern**
   - Always: `/property/:parcelId`
   - Tab access: `/property/:parcelId/:tab`
   - No alternative URLs (legacy routes redirect)

3. **Tab-Based Suite Integration**
   - Each suite provides a tab via `WorkbenchExtension` interface
   - OS orchestrates tabs, badges, quick actions
   - Suites cannot bypass or replace Workbench

4. **Shared Context Ribbon**
   - OS-level ribbon shows parcel identity + statuses
   - Suites contribute badges via extension API
   - Persistent across all tabs

### Consequences

**Positive:**
- ✅ Single source of truth for parcel UI
- ✅ Consistent user experience across all workflows
- ✅ Future suites (Clerk, Treasury, Auditor) integrate cleanly
- ✅ Reduced code duplication (1 workbench vs N parcel screens)
- ✅ Easier maintenance and testing

**Negative:**
- ⚠️ Requires suite refactoring to adopt extension API
- ⚠️ Migration effort from legacy parcel screens
- ⚠️ OS team becomes bottleneck for Workbench changes (mitigated by extension API)

**Neutral:**
- ℹ️ Workbench is now a critical path component
- ℹ️ Performance of Workbench affects all suites

### Implementation

**Files:**
- `os-platform/core/property-workbench/`
- `os-platform/core/interfaces/WorkbenchExtension.ts`
- `os-platform/core/services/WorkbenchOrchestrator.ts`

**Validation:**
- Every suite MUST implement `WorkbenchExtension`
- Deployment blocked if suite lacks extension implementation
- Legacy routes MUST redirect to `/property/:id/:tab`

### Compliance

This decision is **IMMUTABLE**. Any proposal to create suite-specific parcel screens is rejected.

## ADR-0002: Suite Ownership + Write-Lane Matrix

**Status:** ACCEPTED  
**Deciders:** TerraFusion Architecture Team  
**Date:** 2026-01-28  

### Context

With multiple suites operating on the same data (parcels, valuations, permits, etc.), without explicit ownership rules we risk:

- **Write conflicts** - two suites updating the same entity
- **Data corruption** - inconsistent state from concurrent writes
- **Audit ambiguity** - unclear who is authoritative source
- **Architectural drift** - suites expanding into each other's domains

### Decision

**Each data entity has exactly ONE owning suite that can write it.** Other suites can READ via APIs but cannot WRITE.

**Write-Lane Matrix:**

| Data Entity | Owner | Write Permission | Read Permission |
|-------------|-------|-----------------|-----------------|
| Parcel Core | OS Core | `os:parcel:write` | `*` |
| Ownership | OS Core | `os:ownership:write` | `*` |
| Global Flags | OS Core | `os:flags:write` | `*` |
| Valuation Models | TerraForge | `forge:models:write` | `forge:read` |
| Comparables | TerraForge | `forge:comps:write` | `forge:read` |
| GIS Layers | TerraAtlas | `atlas:layers:write` | `atlas:read` |
| Permits | TerraDais | `dais:permits:write` | `dais:read` |
| Exemptions | TerraDais | `dais:exemptions:write` | `dais:read` |
| Appeals | TerraDais | `dais:appeals:write` | `dais:read` |
| Dossier Items | TerraDossier | `dossier:items:write` | `dossier:read` |
| Trace Events | OS Core | `os:trace:write` | `os:trace:read` |

**Forbidden Cross-Suite Writes:**
- ❌ TerraForge CANNOT write permits (TerraDais owns)
- ❌ TerraDais CANNOT write valuations (TerraForge owns)
- ❌ TerraAtlas CANNOT write exemptions (TerraDais owns)

**Allowed Cross-Suite Reads:**
- ✅ TerraForge can READ permits to flag revaluation triggers
- ✅ TerraDais can READ valuations to generate notices
- ✅ TerraAtlas can READ all entities for map overlays

### Implementation

**Enforcement:**

```typescript
// API middleware validates writes
function validateWriteLane(
  entity: DataEntity,
  suite: SuiteName
): void {
  const owner = WRITE_LANE_MATRIX[entity.type].owner;
  
  if (owner !== suite && owner !== "os") {
    throw new WriteLaneViolationError(
      `Suite "${suite}" cannot write "${entity.type}" (owned by "${owner}")`
    );
  }
}
```

**Validation:**
- Pre-deployment: scan all API endpoints, verify write-lane compliance
- Runtime: middleware blocks cross-suite writes
- Violations logged to TerraTrace for audit

### Consequences

**Positive:**
- ✅ No write conflicts between suites
- ✅ Clear ownership and accountability
- ✅ Simplified debugging (one source of writes per entity)
- ✅ Easier to reason about data flow

**Negative:**
- ⚠️ Cross-suite workflows require API calls (not direct DB access)
- ⚠️ Requires discipline to respect boundaries

**Neutral:**
- ℹ️ Read-heavy suites (Atlas) have no restrictions
- ℹ️ OS Core writes are privileged (can write core entities)

### Compliance

This decision is **IMMUTABLE**. Any PR that violates write-lane matrix is auto-rejected.

## ADR-0003: TerraTrace is Unified Append-Only Audit Spine

**Status:** ACCEPTED  
**Deciders:** TerraFusion Architecture Team  
**Date:** 2026-01-28  

### Context

Government systems require comprehensive audit trails for:
- **Compliance** (FISMA, NIST 800-53)
- **Legal defense** (appeals, litigation)
- **Accountability** (who did what when)
- **Debugging** (system behavior reconstruction)

Without a unified approach:
- Each suite creates its own logs (fragmentation)
- Inconsistent retention policies
- Difficult to reconstruct cross-suite workflows
- No single audit trail for parcel activity

### Decision

**TerraTrace is the single, append-only audit trail for ALL suites.**

**Core Principles:**

1. **Append-Only Architecture**
   - Events CANNOT be updated in-place
   - Pattern: `tool_invoked` → `tool_succeeded` / `tool_failed` (separate events)
   - Immutability enforced at database and API layer

2. **Universal Event Model**
   ```typescript
   interface TraceEvent {
     id: string;
     timestamp: DateTime;
     countyId: string;            // Sovereign isolation
     parcelId?: string;
     dossierId?: string;
     actor: Actor;
     event: { suite, module, action, category };
     data: { inputs, outputs, metadata };
     compliance: { classification, retention, auditRequired };
   }
   ```

3. **Suite-Agnostic Logging**
   - All suites emit to TerraTrace via `TraceService.emit()`
   - No suite-specific log tables
   - Activity feed reconstructed from Trace

4. **Retention & Redaction**
   - Retention schedules by event category
   - PII redaction via new redacted events (original preserved)
   - Automated retention enforcement

### Implementation

**Files:**
- `os-platform/core/services/TraceService.ts`
- `os-platform/core/models/TraceEvent.ts`
- `backend/TerraFusion.Data/Entities/TraceEvent.cs`

**Database:**
- PostgreSQL with append-only constraints
- Indexed on: `countyId`, `parcelId`, `timestamp`, `event.action`
- Partitioned by year for performance

**Enforcement:**
- `TraceService.update()` throws exception
- Redaction creates new event, flags original
- Retention policies run nightly

### Consequences

**Positive:**
- ✅ Complete audit trail across all suites
- ✅ Single query to reconstruct parcel history
- ✅ Consistent retention and redaction
- ✅ Compliance-ready (immutable logs)

**Negative:**
- ⚠️ Storage grows (append-only + no deletes until retention)
- ⚠️ Requires suite discipline (emit events for all actions)

**Neutral:**
- ℹ️ Suites must include Trace calls in all workflows
- ℹ️ TerraTrace is critical path (all actions logged)

### Compliance

This decision is **IMMUTABLE**. Suites CANNOT create alternative logging systems.

## ADR-0004: TerraPilot is OS Feature with Pilot/Muse Modes

**Status:** ACCEPTED  
**Deciders:** TerraFusion Architecture Team  
**Date:** 2026-01-28  

### Context

Users need AI assistance for both:
- **Operational tasks** (run models, assign tasks, check statuses)
- **Creative tasks** (draft notices, explain decisions, summarize evidence)

Options considered:
1. Two separate copilots (TerraAssistant + TerraAgent)
2. Suite-specific copilots (ForgeAI, AtlasAI, DaisAI)
3. Single copilot with contextual modes

### Decision

**TerraPilot is a single OS-level personal copilot with two modes:**

```
TerraPilot
├── PilotProfile (user's persistent avatar)
├── Pilot Mode (operator: do/route/act)
└── Muse Mode (creator: draft/explain/synthesize)
```

**Mode Definitions:**

- **Pilot Mode** (Default)
  - Purpose: Execute tasks, route workflows, check statuses
  - Tools: Run models, assign tasks, generate notices, fetch data
  - Risk Levels: All levels (read-only → irreversible)
  - Auto-execution: Low-risk tools only

- **Muse Mode**
  - Purpose: Draft, explain, summarize, synthesize
  - Tools: Write narratives, explain decisions, create templates
  - Risk Levels: Primarily low-risk (drafts)
  - Publishing: Requires separate high-risk tool in Pilot Mode

**Mode Switching:**
- User-initiated (toggle in UI)
- Auto-suggested (when intent detected, e.g., "draft notice")
- Never auto-switch for high-risk tools

### Permission Model

**Split Architecture (CRITICAL):**

```typescript
interface UserPermissions {
  rbacClaims: string[];      // Role-based access control
  allowedTools: string[];    // Tool IDs user can invoke
  dataAccess: AccessLevel;   // Read-only | Standard | Elevated
  countyScope: string[];     // County isolation
}
```

**Tool Risk Levels:**
- `read-only` - No confirmation needed
- `write-low-risk` - Drafts, notes (no confirmation)
- `write-medium-risk` - Workflow actions (confirmation required)
- `write-high-risk` - Approvals, decisions (confirmation + reason code)
- `irreversible` - Roll cert, deletions (confirmation + reason + supervisor)

### Human-in-the-Loop Policy

**Core Rule:** TerraPilot can RECOMMEND high-impact actions but CANNOT execute without explicit human approval.

**Approval Requirements:**

| Risk Level | Confirmation | Reason Code | Supervisor |
|------------|-------------|-------------|-----------|
| Read-Only | ❌ | ❌ | ❌ |
| Write-Low | ❌ | ❌ | ❌ |
| Write-Medium | ✅ | ❌ | ❌ |
| Write-High | ✅ | ✅ | ⚠️ Configurable |
| Irreversible | ✅ | ✅ | ✅ Required |

**Muse Publishing Policy:**
- Muse can draft anything (low-risk)
- Publishing requires separate high-risk tool
- Drafts saved to Dossier with "requires review" flag

### Implementation

**Files:**
- `os-platform/core/terra-pilot/`
- `os-platform/core/models/PilotProfile.ts`
- `os-platform/core/services/TerraPilotService.ts`
- `os-platform/core/components/TerraPilotPanel.tsx`

**Integration Points:**
- Global header (always available)
- Property Workbench (dedicated tab)
- Suite panels (dockable)

**Enforcement:**
- Mode validation (tools locked to mode)
- Permission checks (RBAC + allowlist)
- Approval workflows (based on risk level)
- Trace logging (every action)

### Consequences

**Positive:**
- ✅ One copilot concept (no user confusion)
- ✅ Contextual assistance (mode-appropriate tools)
- ✅ Government-safe (human approval for high-risk)
- ✅ Consistent experience across suites

**Negative:**
- ⚠️ Mode switching adds UI complexity
- ⚠️ Approval workflows slow down power users (mitigated by risk levels)

**Neutral:**
- ℹ️ Users learn two modes vs. one copilot
- ℹ️ High-risk tools require discipline

### Compliance

This decision is **IMMUTABLE**. No suite-specific copilots allowed. TerraPilot is the canonical AI assistant.

## ADR Compliance

### How to Use These ADRs

**For Implementers:**
- Read ADRs BEFORE designing new features
- ADRs override all other documentation
- Violations of ADRs = rejected PRs

**For Architects:**
- New ADRs require team review + approval
- ADRs can be superseded but NOT deleted
- Superseded ADRs marked "SUPERSEDED" with pointer to replacement

**For Reviewers:**
- Check PRs against ADR compliance
- Use ADRs as justification for rejections
- Escalate ADR conflicts to architecture team

### Enforcement

**CI/CD Gates:**
```yaml
adr-compliance-check:
  stage: validate
  script:
    - npm run validate:write-lanes
    - npm run validate:trace-logging
    - npm run validate:workbench-extensions
    - npm run validate:naming-conventions
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: always
  allow_failure: false
```

**Automated Checks:**
- Write-lane validation (ADR-0002)
- Trace logging presence (ADR-0003)
- Workbench extension compliance (ADR-0001)
- Permission model split (ADR-0004)
- Canonical naming (all ADRs)

### Modification Process

1. Propose ADR change in architecture review
2. Document reason for change
3. Get unanimous approval from architecture team
4. Create new ADR (ADR-XXXX) that supersedes old ADR
5. Update old ADR with "SUPERSEDED" status + pointer

**Example:**
```
## ADR-0001: Property Workbench is Tier-0 OS Surface

**Status:** SUPERSEDED by ADR-0042  
**Superseded Date:** 2027-06-15  
**Reason:** [Link to ADR-0042]
```
