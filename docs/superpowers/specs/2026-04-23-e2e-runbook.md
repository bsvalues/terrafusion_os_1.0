# Running the County Studio + Atlas E2E proof

The Playwright spec at `frontend/tests/integration/county-studio-atlas-flow.spec.ts`
covers the canonical chunk-1-integration workflow: Forge home → County Studio
chrome → tablist keyboard navigation → Open Study dialog → SegmentTable states →
Atlas Live View top bar + sync badge + map-data status indicator. Screenshots
land in `frontend/test-results/chunk-1-integration-screenshots/*.png` for manual
review.

The spec is written tolerantly — it passes on both an empty database
(DISCONNECTED sync badge, empty-state segment table) and a seeded database
(LIVE badge, data rows). The workflow is what's under test, not any specific
data state.

## Running against local dev stack

Three terminals (or three background processes), then one E2E invocation.

### Terminal 1 — Backend (.NET 8)

```
cd backend
dotnet run --project src/TerraFusion.API
```

Listens on `http://localhost:5000`. Uses the default SQLite connection from
`appsettings.Development.json`. No seeded CountyStudy rows on a fresh DB —
acceptable; the spec tolerates empty state.

If you want data for the "steady state" SegmentTable assertion to show a
populated table, derive segments first (requires an existing study):

```
# Create a study via the API
curl -X POST http://localhost:5000/api/county-study/studies \
  -H "Content-Type: application/json" \
  -d '{"countyId":"benton","taxYear":2026,"studyType":"RatioStudy","baselineVersion":null}'

# Then run the CLI flag with the returned studyId:
dotnet run --project backend/src/TerraFusion.API -- \
  --derive-segments --study-id=<studyId-from-above>
```

### Terminal 2 — Frontend (Vite)

```
cd frontend
export VITE_MAPBOX_ACCESS_TOKEN=<your-token>    # optional — map renders blank without
npm run dev
```

Listens on `http://localhost:5173` (or `$VITE_PORT`). The Vite proxy routes
`/api` to `:5000`.

### Terminal 3 — Playwright

```
cd frontend
npm run test:e2e:county-studio
```

Playwright's webServer block in `playwright.config.ts` is configured to
`reuseExistingServer` in non-CI mode, so it attaches to the Vite instance
already running.

## Running against CI

```
CI=1 npm run test:e2e:county-studio
```

Playwright auto-starts the Vite dev server (and retries failed tests twice
per the config) and expects the backend to be reachable at the proxy target.

## Failure-mode quick reference

- **"Unable to find role 'tablist'"**: tab-bar a11y didn't land; verify commit
  `f5e0f1066` is in the branch.
- **"tabpanel" not visible**: CountyStudyPage failed to mount — check the
  module registration in `moduleComponents.tsx`.
- **Atlas top bar text missing**: `/forge/atlas-live` route not registered or
  the module lazy-load threw — check browser console.
- **Map-data loading indicator stuck**: the `/geoforge/v2/neighborhoods/outline`
  or `/v2/parcels/tiles` endpoint is unreachable — backend not running, or
  Vite proxy not configured for the v2 paths.

## What this proves when all six tests pass

The delivered slice works end-to-end: module registration → navigation entry
point → page chrome → a11y-compliant tab navigation → data-loading lifecycle
(loading / success / error) for both Segment data and Atlas map data →
Atlas hub subscribe → cross-page state reflection.

The only thing NOT proved by the spec is per-parcel flat-dollar recompute
accuracy — that's covered by the backend unit test
`FlatDollarAdjustment_WithParcels_RecomputesFromShiftedRatios` which runs
on every `dotnet test`.
